Status 欄（NEW）：型別 enum，值只有 ACTIVE / INACTIVE 兩個，NOT NULL，預設 ACTIVE。
顯示：ACTIVE 綠底 Active；INACTIVE 灰底 Inactive 且整列以灰階呈現，讓操作員一眼掃出哪些是停用的。
不要引入參考截圖上的 Blocked 與 Verify Status——那是別的系統的欄位，本系統沒有。
Actions 欄：既有 Edit（鉛筆）與 Delete（紅 X）位置與權限都不變，新增 Activate / Deactivate 按鈕。
ACTIVE 的列出現 Deactivate；INACTIVE 的列出現 Activate。兩者互斥，不會同時出現。
狀態可逆：ACTIVE ⇄ INACTIVE 雙向可切換，沒有終態。
Deactivate 的兩個擋門——兩者的前端行為刻意不同，依「前端有沒有判斷資料」決定
① 預設帳號不可停用：Default Value 前端清單本來就有，可以直接判斷 → Deactivate disable ＋ 說明文字，操作員先去 Edit 把預設改給別筆。後端仍要擋，回 409 BINDING_ACCOUNT_IS_DEFAULT。
② 有處理中提款單不可停用：前端沒有這筆資料，無法預先判斷 → 按鈕可以按，按下後依 API 回應顯示錯誤（點第三列的 Deactivate 看效果）。後端回 409 BINDING_ACCOUNT_HAS_PENDING_WITHDRAWAL。
兩個 409 用不同錯誤鍵，前端才能顯示對應原因。
這兩種都是業務規則造成的不可操作，一律附原因說明，不用隱藏——操作員要知道為什麼不能按、下一步做什麼。權限不足才用隱藏（見下一則）。
併發保護：後端檢查「有無處理中提款單」與寫入 INACTIVE 要在同一交易內並對該筆取鎖，否則會出現檢查通過後、寫入前剛好有人建立提款單的競態。
權限：由後台權限節點控制，不綁 4-tier 層級（user 2026-08-14 拍板）。
被授予「綁定帳號狀態管理」權限的操作者就能執行，與他是 Admin 還是 Sub Agent Admin 無關。因此要新增一個對應的權限節點掛進既有權限設定畫面（節點名稱與位置由 RD 依既有結構決定）。
權限不足時按鈕直接隱藏，不是 disable——本 BO 既有慣例（user 2026-08-13 確認）。切上方權限開關到「無此權限」可看到效果：Activate / Deactivate 消失，Edit / Delete 仍在。
Delete 的權限維持現狀不動（user 拍板），不因本需求收緊，所以它不受這個新權限節點影響。
前端隱藏只是顯示層，後端一律要驗權並回 403，不可只靠前端。
⚙ Dev Notes / RD 開發邊界（點擊展開，正式 demo 可收合）▼

1. 狀態機

  • 欄位 status，型別 enum('ACTIVE','INACTIVE')，NOT NULL，預設 ACTIVE。
  • 轉換：ACTIVE → INACTIVE（Deactivate）、INACTIVE → ACTIVE（Activate）。雙向可逆，無終態。
  • 既有資料 migration：所有現存綁定帳號一律填 ACTIVE。
  • 玩家層級的 Block 是另一個軸，與本欄位無關，本需求不碰。

2. 唯一性約束（本需求的技術核心）

  • 自然鍵依 Binding Type 分：Bank Card = 銀行 ＋ 帳號；E-Wallet = 錢包位址；Pulsa = 手機號。
  • 唯一範圍涵蓋 INACTIVE——停用的資料繼續佔用該帳號，其他玩家不能註冊。這與一般軟刪除「刪掉即釋放」相反，是客戶的明確訴求。
  • 原玩家自己也擋：同一玩家重加自己已停用的帳號同樣撞唯一鍵，UI 引導改用 Activate。因此不需要 partial index，單純全表唯一即可。
  • 擋在 DB unique index ＋ 應用層，前端只做提示，不可只靠前端。

3. Delete 的邊界（刻意保留的逃生門，非疏漏）

  • Delete 保留、權限不動（user 2026-08-13 拍板）。刪除會真的清掉資料並釋放唯一鍵，該帳號之後可被其他玩家註冊。
  • 因此 Delete 是繞過「停用後帳號被佔住」的合法路徑。user 已知悉，選擇以二次確認的文案提示處理，不以權限封鎖。
  • 二次確認的文案必須明講「刪除後此帳號可被其他玩家註冊」與「若只是暫停使用請改用 Deactivate」，否則操作員會照舊習慣按 Delete，這個需求等於白做。

4. API 形態

Method / Path用途錯誤碼
PATCH /players/{playerId}/binding-accounts/{id}/deactivate停用單筆403 權限不足 / 409 預設帳號 / 409 有處理中提款單 / 404 不存在
PATCH /players/{playerId}/binding-accounts/{id}/activate啟用單筆403 權限不足 / 404 不存在
  • 採兩個獨立路徑，不用 action_type 參數區分——權限控管與審計記錄比較好寫。
  • 操作對象是單筆，以該筆綁定帳號的 id 指定，不接受批次。
  • 兩個 409 要用不同的錯誤代碼或訊息鍵區分，前端才能顯示對應的原因。

5. 會員端（FE）影響

  • FE 的提款帳號選單只取 status = ACTIVE。停用的帳號不得出現。
  • 此項需 FE 團隊同步改動，不是 BO 單邊可完成，已列 ASM。

6. 審計

  • 每次 Activate / Deactivate 都要留紀錄：操作者、時間、對象綁定帳號、變更前後值。
  • 落點待 RD 確認：Player's Info 已有 Update History 分頁，若其機制已涵蓋綁定帳號異動則沿用，未涵蓋則另建。已列 ASM。

7. 本期範圍外

  • 不引入 Verify Status、不引入 Blocked（皆為參考截圖上其他系統的欄位）。
  • 不動玩家層級 Block、不動提款流程與退款邏輯、不動 Edit 對話框既有欄位。
  • 不回補既有已刪除的綁定帳號（user 2026-08-14 拍板）。那些帳號的自然鍵維持可用，其他玩家可以註冊。

撞號分兩種，訊息要不一樣：
① 撞到同一玩家自己的停用資料 → 就是本畫面，明確引導改用 Activate。
② 撞到其他玩家的資料（不論啟用或停用）→ 不得揭露是誰，只回一般性訊息如 This account is already registered.。揭露其他玩家的綁定關係屬個資外洩。
兩種都由後端判定並回不同錯誤鍵，前端不自行推斷。

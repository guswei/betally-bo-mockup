# Binding Account 啟用／停用 — RD 開發 Spec

- 對象系統：GCP Agent BO
- 位置：`2.1 Player List` → `Player's Info` → 頁面下方 `Binding Account` 分頁
- Mockup：`_workspace/binding_account_status_mockup.html`（開啟後右上可切換「顯示 RD 註記」）

---

## 1. 背景與範圍

綁定帳號目前只能新增與刪除。客服要暫停一個帳號時，只能把它刪掉，之後再重建，帳號的歷史資料就此消失。客戶要求改為可以停用與啟用，資料留著、但不讓玩家在前台看到。

本次做三件事：

1. 綁定帳號新增 `status` 欄位與對應的 Activate／Deactivate 操作。
2. 綁定帳號的唯一性約束改為涵蓋停用中的資料。
3. 既有的刪除動作加上二次確認。

---

## 2. 資料模型變更

### 2.1 新增欄位

| 欄位 | 型別 | 約束 | 說明 |
|---|---|---|---|
| `status` | `enum('ACTIVE','INACTIVE')` | `NOT NULL`，預設 `ACTIVE` | 綁定帳號的啟用狀態 |

既有欄位不動。

### 2.2 既有資料 migration

所有現存綁定帳號一律填入 `ACTIVE`。

建立唯一索引前必須先做重複資料盤查（preflight）。既有資料表沒有這條約束，可能已存在同一自然鍵的多筆資料。盤查結果有重複時，先產出重複清單交由營運決定保留哪一筆，處理完才建立索引。

部署順序：新增 `status` 欄位並回填 → 執行重複盤查 → 建立唯一索引 → 開啟前端功能。

Rollback 方向：移除唯一索引與 `status` 欄位即可回到原狀。已被停用的綁定帳號在 rollback 後會回到可用狀態，需要在 rollback 前確認營運可接受。

### 2.3 唯一性約束

自然鍵依 `Binding Type` 分，比對前一律先正規化：

| Binding Type | 自然鍵 | 正規化規則 |
|---|---|---|
| Bank Card | 銀行識別 ＋ 銀行帳號 | 帳號去除空白與連字號，只留數字；銀行以既有銀行代碼比對，不用顯示名稱 |
| E-Wallet | 錢包位址 | 去除前後空白，英文字母一律轉小寫 |
| Pulsa | 手機號碼 | 統一轉為國碼格式。`0` 開頭的本地格式一律轉為 `+62` 開頭後再比對 |

正規化後的值另存一個比對用欄位，唯一索引建在該欄位上，原始輸入值照樣保留供顯示。

沒有正規化的話，同一支手機號用 `+6285575757` 與 `085575757` 兩種寫法就能各註冊一次，唯一性約束等於失效。

唯一範圍**涵蓋 `INACTIVE` 的資料**。停用中的綁定帳號繼續佔用該自然鍵，其他玩家無法用同一組資料註冊。

三種 `Binding Type` 各自獨立比對，不同型態之間不互相排斥。

同一玩家重新新增自己已停用的帳號，同樣撞唯一鍵。因此唯一索引為單純的全表唯一，不使用條件式索引（partial index）。

刪除會移除資料列並釋放該自然鍵，被刪除的帳號之後可由其他玩家註冊。

## 3. 畫面變更

### 3.1 清單新增欄位

`Status` 欄放在清單**最後一欄**，既有欄位的順序與內容不動。

| `status` 值 | 顯示 | 列的呈現 |
|---|---|---|
| `ACTIVE` | 綠底徽章 `Active` | 一般 |
| `INACTIVE` | 灰底徽章 `Inactive` | 整列灰階 |

### 3.2 篩選新增

篩選區新增 `Status` 下拉，選項 `ALL` / `Active` / `Inactive`，預設 `ALL`。既有的 `Binding Account Type` 篩選不動。

### 3.3 Actions 欄

既有的編輯與刪除圖示，位置與權限都不動。新增：

| 列的 `status` | 出現的按鈕 |
|---|---|
| `ACTIVE` | `Deactivate` |
| `INACTIVE` | `Activate` |

兩個按鈕互斥，同一列不會同時出現。

---

## 4. 操作與規則

### 4.1 Deactivate

把 `status` 從 `ACTIVE` 改為 `INACTIVE`。

**兩個阻擋條件，前端與後端都要擋：**

| 條件 | 前端 | 後端 |
|---|---|---|
| 該筆為預設帳號（`Default Value = true`） | 按鈕 `disabled`，附說明文字引導先變更預設 | 回 `409` |
| 該綁定帳號有處理中的提款單 | 依 API 回應顯示原因 | 回 `409` |

兩個 `409` 使用不同的錯誤鍵：預設帳號為 `BINDING_ACCOUNT_IS_DEFAULT`，有處理中提款單為 `BINDING_ACCOUNT_HAS_PENDING_WITHDRAWAL`。前端依錯誤鍵顯示對應原因。

前端無法即時判定有沒有處理中的提款單，這一項以 API 回應為準。前端不預先 disable 停用按鈕，按下後依 API 回應顯示原因。預設帳號的判定資料前端已經有，該情況才在前端 disable。

**併發保護**：檢查「有無處理中提款單」與寫入 `status = INACTIVE` 必須在同一個交易內完成，並對該綁定帳號取鎖。否則會出現檢查通過之後、寫入之前，另一個交易剛好建立提款單的競態，結果是一筆處理中的提款掛在已停用的帳號上。

同一把鎖也要涵蓋提款建立那一側：建立提款單時檢查帳號 `status` 與停用時檢查提款單，兩者必須互斥。

停用後的效果：

- 該筆仍留在 BO 清單，狀態顯示 `Inactive`。
- 該筆不出現在會員端，玩家無法用它提款。
- 該筆的自然鍵繼續被佔用。

停用不需要勾選式二次確認。這個操作可逆且不刪資料。

### 4.2 Activate

把 `status` 從 `INACTIVE` 改為 `ACTIVE`。

啟用後該筆恢復顯示於會員端，玩家可照常使用。

`Default Value` 不因啟用而改變。預設帳號無法被停用，所以停用中的帳號一定不是預設帳號，啟用回來也不自動設為預設。

`ACTIVE` 與 `INACTIVE` 雙向可切換，沒有終態。

### 4.3 Delete

刪除的權限與行為維持現狀，不因本次需求收緊。

新增二次確認對話框，須勾選確認框後才能送出。文案必須傳達兩件事：

1. 刪除後這個帳號可以被其他玩家重新註冊。
2. 若只是要暫停使用，改用 Deactivate。

對應的英文 UI 文案見 mockup 的 Delete 對話框。

### 4.4 Add 撞號

新增綁定帳號撞到唯一鍵時，依撞到的對象回不同訊息：

| 撞到的對象 | 訊息方向 |
|---|---|
| 同一玩家自己的停用資料 | 明確告知該帳號已存在且為停用中，引導改用 Activate |
| 其他玩家的資料（不分啟用或停用） | 只回一般性的「此帳號已被註冊」，**不得揭露是哪一位玩家** |

揭露其他玩家的綁定關係屬個資外洩。判定由後端做並回不同錯誤鍵，前端不自行推斷。

## 5. API

| Method / Path | 用途 |
|---|---|
| `PATCH /players/{playerId}/binding-accounts/{id}/deactivate` | 停用單筆 |
| `PATCH /players/{playerId}/binding-accounts/{id}/activate` | 啟用單筆 |

採兩個獨立路徑，不用 `action_type` 參數區分動作。

操作對象是單筆，以綁定帳號的 `id` 指定，不接受批次。

錯誤模型：

| 狀態碼 | 錯誤鍵 | 情境 |
|---|---|---|
| `403` | `FORBIDDEN` | 權限不足 |
| `404` | `BINDING_ACCOUNT_NOT_FOUND` | 綁定帳號不存在，或該 `id` 不屬於路徑上的 `playerId` |
| `409` | `BINDING_ACCOUNT_IS_DEFAULT` | 停用預設帳號 |
| `409` | `BINDING_ACCOUNT_HAS_PENDING_WITHDRAWAL` | 該帳號有處理中的提款單 |

`id` 不屬於路徑上的 `playerId` 時一律回 `404`，不回 `403`。回 `403` 等於告訴呼叫端「這筆存在但不是你的」，會洩漏其他玩家的綁定帳號是否存在。

重複操作視為成功：對已經是 `INACTIVE` 的綁定帳號呼叫 deactivate，回 `200` 且不變更資料；activate 同理。這讓前端重送與網路重試不會產生錯誤。

## 6. 權限

啟用與停用**由後台權限設定控制，不綁定 4-tier 層級**。被授予該權限的操作者即可執行，與其在 Admin / Brand Admin / Agent Admin / Sub Agent Admin 的哪一層無關。

因此需要一個對應的權限節點，掛在既有的權限設定畫面，供後台勾選。

| 操作 | 授權方式 |
|---|---|
| Activate / Deactivate | 新增的權限節點，由後台設定 |
| Edit / Delete | 維持現狀，沿用既有權限 |

**權限不足時按鈕直接隱藏**，不使用 `disabled`。這是本 BO 的既有慣例。

因業務規則而不可操作的情況（預設帳號、有處理中提款單）另外處理，那些用 `disabled` 加說明文字，讓操作員知道原因與下一步。

前端隱藏只是顯示層。後端一律要驗權，權限不足回 `403`。

---

## 7. 停用帳號的提款阻擋（前後端各一層）

### 7.1 前端（會員端）

會員端的提款帳號選單只取 `status = ACTIVE` 的綁定帳號。停用中的帳號不得出現在選單。

這一層需要 FE 同步改動，不是 BO 單邊可以完成。

### 7.2 後端（提款建立 API）

**提款建立 API 必須在後端驗證綁定帳號的 `status`。** `status` 不是 `ACTIVE` 時拒絕建立提款單，回 `409`，錯誤鍵 `BINDING_ACCOUNT_INACTIVE`。

只做前端過濾不足以達成需求。舊版 App、已載入的頁面快取、直接呼叫 API 這三種情況都繞得過選單過濾。停用帳號的目的是不讓錢出去，這條防線必須落在後端。

本項屬既有提款建立流程的**帳號資格驗證**，列入本次範圍。提款的其他環節（審批、派單、退款、狀態流轉）不變。

---

## 8. 審計

每次 Activate 與 Deactivate 都要寫入一筆異動紀錄，內容包含：操作者、時間、對象綁定帳號 `id`、`status` 變更前的值、變更後的值。

紀錄沿用 `Player's Info` → `Update History` 的既有異動紀錄機制與查詢入口，不另建資料表與查詢頁面。既有機制的資料結構若無法容納綁定帳號層級的對象識別，以擴充該機制為準。

保存期限沿用既有異動紀錄的規則。

---

## 9. 範圍外

- 不引入 `Verify Status` 欄位。
- 不引入 `Blocked` 狀態。綁定帳號只有 `ACTIVE` 與 `INACTIVE` 兩個值。
- 不動玩家層級的 `Block` 功能，那與綁定帳號狀態是不同的軸。
- 不動提款的審批、派單、退款與狀態流轉。提款建立時的帳號資格驗證屬本次範圍，見第 7.2 節。
- 不動 Edit 對話框的既有欄位。
- 不動 Delete 的權限。
- 不回補既有已刪除的綁定帳號資料。這些帳號的自然鍵維持可用，其他玩家可以註冊。
- 不做批次啟用或批次停用。

---

## 10. 金額精度

本次不新增金額欄位。既有提款金額欄位維持 `DECIMAL(18,2)`，本次不變更其精度，也不得改用浮點數。

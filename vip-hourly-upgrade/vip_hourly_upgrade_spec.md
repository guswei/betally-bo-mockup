# VIP 等級升級每小時檢查 RD Spec

- 版本：v1.0
- 日期：2026-08-13
- 平台：Agent BO（GCP）
- 對應需求：`_workspace/vip_hourly_upgrade_PRD.md`

## 1. 背景與目標

VIP 等級升級目前每天執行一次。後端需改為讀取可維護的執行間隔，預設每 `60` 分鐘檢查一次，讓達標玩家在下一次 job 執行時升級。VIP 只能升級，job 不得降低玩家等級。

## 2. 範圍

IN：

- VIP 升級 job 的排程週期與時區處理
- VIP 達標等級計算後的只升不降規則
- 跨級時逐級發放升等獎金
- 升級與獎金的冪等及併發防護
- `System Config` → `VIP` tab 的執行間隔設定、權限與稽核
- 既有 CleverTap `VIP Upgrade` 事件

OUT：

- VIP 達標條件及存款額／流水額計算方式
- VIP 自動降級
- `Payment Level`
- `Allow VIP Bonus` 玩家開關的既有行為
- BO 手動調整 VIP 的既有行為
- 新頁面、完整 mockup 與對外 API

## 3. 功能契約

### 3.1 排程與設定

1. job 從既有 System Config 機制讀取 VIP upgrade interval。
2. 設定值型別為 `INT`，單位為分鐘，預設 `60`，下限 `60`。
3. 設定值可在大於或等於 `60` 的整數間調整。可從較大值改回 `60`，不接受小於 `60` 的值。
4. 前端送出前驗證，後端保存前再次驗證。後端收到小於 `60` 或非整數值時拒絕保存，原值不變。
5. job 採 fixed-rate 排程。設定儲存成功後，以儲存時間為基準按新間隔計算下一次觸發；正在執行的 job 不受影響。
6. 同一時間只允許一個 job instance。新觸發發生時若前一次尚未結束，跳過新觸發並記錄一次重疊跳過，不排隊、不併發。
7. 排程與達標時間計算一律使用 `GMT+07:00`。

### 3.2 VIP 狀態轉換

| 現有等級與達標等級關係 | 結果 |
|---|---|
| 達標等級高於現有等級 | 更新至達標等級，並處理所有中間等級 |
| 達標等級等於現有等級 | 不更新 |
| 達標等級低於現有等級 | 不更新，不降級 |

計算規則固定為 `新等級 = max(現有等級, 達標等級)`。BO 手動調高的 VIP 等級不得被 job 下調。

### 3.3 跨級獎金

玩家從現有等級升到較高等級時，後端依等級順序逐級處理。例如 `VIP0 → VIP3` 必須處理 VIP1、VIP2、VIP3，各發一筆該級既有獎金。每級金額沿用既有設定，儲存與計算使用 `DECIMAL(18,2)`，不得使用 float。

`Allow VIP Bonus` 的既有判斷維持不變。逐級處理只改變獎金對應的目標等級，不改變玩家是否可領獎的既有條件。job 執行頻率改變前後，同一條等級路徑的總發放金額必須相同。

### 3.4 冪等與交易邊界

1. 業務冪等鍵為「玩家 + 目標 VIP 等級」。
2. 持久層需對該業務鍵建立唯一約束。每個業務鍵只保留一筆紀錄，狀態至少能區分 `processing`、`succeeded`、`failed`；應用層預查不能取代唯一約束。
3. 每個目標等級的升級處理、該級獎金與處理結果必須共用可判定成功或失敗的交易邊界。
4. job 重跑、程序重啟或併發執行命中 `succeeded` 時跳過該目標等級，不得重複發獎。命中 `failed` 時鎖定並更新同一筆紀錄後重試，不新增紀錄。
5. `processing` 紀錄只能由取得該筆鎖的 worker 執行；其他 worker 跳過。worker 中斷後，由既有 job timeout 規則把該筆轉為 `failed`，下次 job 依前項重試。
6. 單一玩家的某級處理失敗時，不得把其他玩家已完成的處理回滾。下次 job 可再次處理未成功的目標等級。
7. 玩家跨多級時依序處理；玩家等級只能更新到已完成逐級處理的最高等級。

### 3.5 CleverTap 事件

每次 job 將玩家 VIP 更新至本次已完成的最高等級後，建立一筆既有 CleverTap `VIP Upgrade` 事件送出工作。跨多級只送一筆，`Previous Level (String)` 為本次 job 更新前等級，`New Level (String)` 為本次已完成的最高等級。事件送出工作需以玩家、本次更新前等級與本次更新後等級建立唯一約束。沒有等級異動時不建立。外部發送失敗沿用既有 CleverTap 重試機制；重試不得建立第二筆送出工作，也不得再次發獎。

## 4. BO 設定與權限

### 4.1 欄位

| 項目 | 契約 |
|---|---|
| 路徑 | `System Config` → `VIP` tab |
| 欄位 | VIP upgrade interval (minutes) |
| 型別 | `INT` |
| 必填 | 是 |
| 預設值 | `60` |
| 最小值 | `60` |
| 時區 | `GMT+07:00` |

不新增頁面。`2.1 Player List` → `Player's Info` 右側 VIP 區塊不調整。

### 4.2 權限矩陣

| 操作者 | 檢視設定 | 修改設定 | 後端授權 |
|---|---|---|---|
| Admin | 可 | 可 | 允許 |
| Brand Admin | 可 | 可 | 允許 |
| 非 Admin / Brand Admin | 依既有 System Config 可見性 | 不可 | 拒絕 |

前端隱藏或 disabled 不能取代後端授權。未授權請求不得變更設定值。

### 4.3 稽核

設定修改沿用既有 System Config 稽核機制，至少記錄操作者、修改時間、修改前值與修改後值。驗證失敗或未授權的請求不得產生成功變更紀錄。

## 5. 資料與 migration

| 資料 | 型別／精度 | 約束 |
|---|---|---|
| VIP upgrade interval | `INT` | `NOT NULL`、default `60`、值不得小於 `60` |
| VIP 升等獎金 | `DECIMAL(18,2)` | 沿用各等級既有金額，不得使用 float |
| 玩家 + 目標 VIP 等級 | 既有識別型別 | 業務唯一約束；狀態為 `processing`、`succeeded` 或 `failed` |

設定值沿用既有 System Config 儲存機制，不新增獨立 table。部署時若既有資料沒有此設定，migration 寫入 `60`；rollback 移除新增設定並停用新排程，不回滾已完成的 VIP 升級、獎金或事件紀錄。冪等紀錄必須保留，避免重新部署後重複發獎。

## 6. 排程處理順序

1. 依 `GMT+07:00` 啟動 job，記錄本次執行識別與開始時間。
2. 讀取 VIP upgrade interval，排程器將該值套用至後續執行。
3. 取得本次需檢查的玩家，依既有規則計算達標等級。
4. 套用 `新等級 = max(現有等級, 達標等級)`；結果未高於現有等級時結束該玩家處理。
5. 由現有等級的下一級開始，依序產生各目標 VIP 等級的業務冪等鍵。
6. 冪等紀錄為 `succeeded` 時跳過該級；為 `failed` 時鎖定並更新同一筆紀錄後重試；不存在時建立 `processing` 紀錄。
7. 將玩家 VIP 更新至已完成處理的最高等級。
8. 玩家等級有異動時，建立一筆既有 CleverTap `VIP Upgrade` 事件送出工作，包含 `Previous Level (String)` 與 `New Level (String)`；跨多級不逐級建立事件。
9. 記錄結束時間與執行統計。

## 7. 失敗、重試與併發

- 唯一約束衝突時讀取既有狀態：`succeeded` 與仍由其他 worker 處理的 `processing` 跳過；`failed` 鎖定原紀錄後重試，不建立第二筆紀錄。
- 單一玩家處理失敗時記錄玩家識別、目標 VIP 等級及失敗原因，繼續處理其他玩家。
- 獎金未成功時不得把玩家等級更新到該目標等級。
- CleverTap 發送失敗不得回滾已完成的 VIP 升級與獎金；事件需以同一升級處理識別重試，且不得再次發獎。
- 同一玩家由兩個 job instance 併發處理時，以持久層唯一約束決定唯一成功結果。

## 8. 觀測性

每次 job 記錄：

- 開始時間與結束時間（`GMT+07:00`）
- 掃描玩家數、無異動玩家數、升級玩家數
- 各目標等級處理成功數、失敗數與冪等跳過數
- 升等獎金成功數、失敗數與金額加總（`DECIMAL(18,2)`）
- CleverTap 事件成功數與失敗數

日誌不得輸出獎金以外的玩家敏感資料。錯誤紀錄需保留足以定位玩家、目標 VIP 等級與本次 job 的識別資訊。
